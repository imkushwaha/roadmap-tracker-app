# `roadmap.json` / `roadmap.js` data shape

Generated by `scripts/md_to_json.py` from `roadmap.md`. `roadmap.js` is the
exact same object, assigned to `window.ROADMAP_DATA`, so the app can load
it via a plain `<script>` tag (no fetch or CORS needed).

```ts
type Roadmap = {
  meta: {
    title: string;
    subtitle: string;
    horizonStart: string;   // ISO date, e.g. "2026-10-01"
    horizonEnd: string;     // ISO date, e.g. "2027-07-31"
    weeklyHours: { min: number; max: number };
    weeklyAllocation: Array<{
      track: string; hoursMin: number; hoursMax: number; priority: string;
    }>;
    depthLevels: Array<{ code: "D3" | "D2" | "D1" | "LOW"; label: string }>;
  };

  phases: Array<{
    id: string;              // e.g. "month-1"
    number: number;          // 1..10
    title: string;           // phase theme, e.g. "Software Engineering Upgrade"
    calendarLabel: string;   // e.g. "OCTOBER 2026"
    startDate: string | null;
    endDate: string | null;
    objective: string;
    exitCriteria: string[];
    sections: Array<{
      id: string;
      title: string;              // e.g. "Week 1 — Python Engineering"
      type: "week" | "theme";
      startDate: string | null;
      endDate: string | null;
      topics: Array<{
        id: string;
        title: string;
        depth: string | null;         // e.g. "D3", "D2/D3"
        kind: "study" | "build" | "benchmark";
        groups: Array<{
          label: string | null;        // e.g. "Study", "Low priority", or null
          subtasks: Array<Subtask>;
        }>;
      }>;
    }>;
    deliverables: Subtask[];     // "Month N deliverables" checklist
    notes: Array<{ id: string; title: string; blocks: string[] }>; // read-only
  }>;

  counters: Array<{
    id: string; label: string; target: number; current: number;
  }>;

  masteryChecklist: Array<{
    id: string; title: string;          // category, e.g. "Concurrency / APIs"
    skills: Array<{
      id: string; title: string; depth: string | null; status: string;
    }>;
  }>;

  reference: Array<{
    id: string; title: string; blocks: string[]; // raw text/markdown-ish blocks
  }>;
};

type Subtask = {
  id: string;               // stable slug, unique across the whole document
  title: string;
  status: "not_started";    // static default; live status lives in the user's saved progress
  notes: string;
  link: string;
  dueDate: string | null;
};
```

## Where progress actually lives

Everything above is **static content** — it has no idea whether you've
done anything. Live progress is stored separately, per user, in the
server's SQLite database (`user_data.data`, a JSON text column, plus an
integer `version` that increments on every save). The document has this
shape (validated by `js/progress-schema.js` on both the browser import and
`PUT /api/data`; unknown top-level keys such as `exportedAt` are ignored):

```ts
type ProgressStore = {
  items: {
    [id: string]: {
      status: "not_started" | "in_progress" | "completed" | "blocked";
      notes: string;
      link: string;
      dueDate: string | null;      // ISO date or null
      completedAt: string | null;  // ISO datetime, set when status becomes "completed"
    };
  };
  counters: { [counterId: string]: number };
  celebratedPhases: string[];   // phase ids already shown a confetti celebration
  settings: { startMonth?: string };   // "YYYY-MM": the month Month 1 begins
  custom: {                     // things the user added themselves
    phases?: Array<{            // extra months, appended after Month 10 (optional)
      id: string;               // "custom-month-…"
      title: string;
      objective?: string;
      sections: Array<{
        id: string;             // "custom-section-…"
        title: string;
        weekNumber: number | null;   // 1-4 = dated week of the month; null = undated
      }>;
    }>;
    topics: Array<{
      id: string;               // "custom-topic-…"
      sectionId: string;        // the section (week) it was added to
      title: string;
      depth: string | null;     // "D1" | "D2" | "D2/D3" | "D3"
      tasks: Array<{ id: string; title: string }>;   // ids are "custom-task-…"
    }>;
  };
};
```

`id` here is any subtask id, deliverable id, or mastery-skill id from the
static data above — they all share one namespace and are guaranteed
unique by the generator. The app merges `ProgressStore.items[id]` over a
default (`not_started`, empty notes/link, no due date) at render time, so
an item with no entry yet is simply "not started".

Custom months are numbered after the built-in ones (Month 11, 12, …), so
their dates follow the start month like any other month. A custom month's
sections hold topics through the same `custom.topics[].sectionId` link, so
topics can be added to a custom section exactly as to a built-in week.
`custom.phases` is optional: data saved before it existed is still valid.

Custom topics are keyed by `sectionId`. If you regenerate `roadmap.json`
and a section's heading text changes, its slug changes too, and custom
topics attached to the old slug stay saved but stop being displayed.

This is exactly what **Export progress** downloads and **Import
progress** reads back in — a backup never needs the roadmap content,
only this store.
